# 纸质委托书

新建委托顶部选择“使用纸质委托书”后，只上传纸质委托书照片，其他信息无需填写。创建后状态为“待处理纸质委托书”，列表保留“纸质委托书”标签，不生成润丰同步事件，也不能派工。

创建事务同时保存照片关联、操作日志和通知队列。通知发送给**所有门店**启用的服务顾问和管理员，复用现有钉钉工作通知发送、结果查询和失败处理机制。`DISPATCH_NOTIFICATION_MODE=dingtalk` 时发送真实通知；禁用时保留队列。通知链接使用 `paperOrder=<委托单ID>`，登录后打开详情。跨店收件人可以只读查看收到通知的纸质委托书及附件，不能修改、关联、派工或提交；普通电子委托单的跨店权限不变。

所属门店的服务顾问或管理员在详情中二选一：

- **已在润丰创建**：输入 `A/B/F/J + 数字` 格式的润丰派工号，按完整派工号精确查找。读取单据、车辆/车型与客户档案、联系人和电话、部门、日期、故障描述、费用及维修项目，保存润丰来源标识。照片保留在“其他照片”。无匹配、多匹配、被其他 H5 单据占用、读取失败或数据无效时整体回滚。关联后的单据标记已同步，不向润丰发送创建事件。后续四项更正可以从同步版本 0 开始产生 `updated` 事件，按原派工号更新，不重复创建。
- **在钉钉创建**：转为由当前处理人负责的草稿，补全正常开单字段；原纸质委托书照片保留；再次打开草稿详情可点击“继续补全钉钉委托单”。无需电子签字及额外维修前照片，点击“提交委托单（免签字）”后进入正常维修流程，激活预选派工（如有），并产生一次润丰 `created` 事件。

在钉钉创建的纸质单尚为草稿时，详情仍显示两种开单方式。负责顾问或本店管理员可继续补全，或改为输入润丰派工号关联；关联成功后以润丰信息替换草稿资料和维修项目，清除草稿预选派工，保留纸质照片。拉取失败时保留原草稿。已经提交、关联润丰或存在同步/派工记录的单据不能再切换开单方式。

## 润丰消费者约定

按派工号关联已有单据时，仅查询润丰正式内账 `qxwxb.wd=''`，避免同派工号的外账记录导致重复匹配；项目明细按所选单据的 `dh` 与 `wd` 读取。正式内账仍有多条匹配时，继续拒绝关联，需核对润丰数据。

钉钉创建的纸质委托单仍使用现有同步队列、API 和版本，额外提供：

```json
{
  "order": {
    "paperOrder": { "mode": "dingtalk", "photoIds": ["file-id"] },
    "signatureExemption": "纸质委托书",
    "signatures": { "customer": "联系人姓名" }
  }
}
```

所有润丰同步事件的 `order.signatures.customer` 统一使用工单联系人（去除首尾空白），联系人为空时填固定文字“联系人”，因此消费者无需为纸质单增加空签名兼容。此字段仅为润丰接口兼容文字，不代表电子签字；真实签名记录和图片保持不变，纸质委托照片仍在现有附件存储中。仅上传照片的待处理记录、关联润丰已有单据的记录不会进入创建队列。

迁移 `202610260004_runfeng_contact_signature.sql` 按事件快照中的联系人更新尚未同步成功的事件，并记录修改前快照；不改已成功同步的历史、不重置领取锁或自动重试。已被消费者读入内存的事件需下一次领取才能取得新数据。发布前应核对同车重复工单，避免重复创建润丰单据。

## 数据与验证

上线前应用新增迁移 `202610170003_paper_work_orders.sql`，再启动新版本。迁移增加 `work_orders.paper_order` 与待处理状态，并允许创建通知在派工任务之前存在。

- `npm run check`：单元测试、TypeScript 和生产构建。
- `PAPER_ORDER_TEST_ADMIN_URL=<本地PostgreSQL管理连接> node --test test/paperOrder.integration.test.mjs`：仅允许本机连接，创建并删除独立测试数据库，验证完整迁移、事务、跨店通知及只读权限、两种处理路径、回滚、重复提交和并发处理。

不自动推送、部署或修改已有应用数据库。

重新上传纸质委托书原照片时，更新 `paperOrder.photoIds` 引用；旧文件保留用于审计，并从当前照片展示中隐藏。纸质单的维修前照片均为选填。
