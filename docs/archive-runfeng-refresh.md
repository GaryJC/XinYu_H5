# 归档从润丰更新

归档查询的“全部从润丰更新（N）”更新当前账号有权限的全部已同步、已签字委托单，N 为符合条件的总数；使用完整归档列表，不受搜索条件和列表分页影响。管理员更新本门店全部符合条件的单据，服务顾问更新自己负责的单据。详情的“从润丰更新”只更新当前单据。批量更新逐单执行，避免同时向润丰发起大量请求；期间需保持页面打开。每单独立提交，显示进度及成功/失败数量，失败列出单号和原因。成功后列表与已打开的详情立即使用数据库返回的新内容，打印也使用新内容。

仅管理员和本单服务顾问可操作，服务端再次校验门店与归属。仅已签字、润丰推送状态为 `synced` 且无未完成 outbox 的单据可反向更新。API：`POST /api/work-orders/:id/refresh-from-runfeng`，返回现有 `WorkOrder` 合同。客户端不传入润丰连接参数、来源行号或待覆盖字段。

优先使用已回填的 `legacy_reid + legacy_document_no` 精确定位 `qxwxb`；没有关联时仅匹配唯一的 `H5:<order.id>` 来源标记并核对现有派工号。不按车牌寻找“最新单”，不从历史分表猜测同号记录。来源缺失、重复或标记冲突时不写入本地数据库。润丰读取在单个 SQL Server SERIALIZABLE 只读事务中完成，不修改润丰业务表，也不产生新的 H5 推送事件。

更新范围：派工号、进厂日期、预计交车日期、车辆与客户资料、故障描述（`wxnr`）、预计费用（`fyhj`）、维修项目名称与工费。车辆车型优先使用委托单 `cx` 解析车型主数据，VIN 由对应车辆档案读取；客户名称和地址由委托单 `ssdw` 对应的客户档案读取。维修项目由相同 `dh + wd` 且 `lb=项目` 的 `qxwxmxb` 行读取，不把材料明细写成维修项目。不更新本系统的门店/顾问归属、业务状态、维修执行状态、结算记录、签名、照片、OCR、平台同步记录和历史留痕。成功更新会追加一条操作留痕。

新增迁移 `202610150002_runfeng_refresh_item_link.sql` 给维修项目保存来源 `reid`。首次更新仅对双方名称均唯一的项目建立关联，后续按来源 ID 匹配，名称修改或重排不会改变本地项目 ID、开完工记录及检验信息。尚未派工且没有领料记录的单据可同步项目增删；已派工、已存在非待派工项目或领料记录时，项目增删或初次匹配不明确会使整单回滚，防止破坏维修进度。此类冲突需要先人工核对两边项目，不会默默覆盖。

PostgreSQL 锁定父委托单直到更新完成，与派工操作遵循同一锁顺序；同步更新派工 JSON 中的项目名称并递增版本，使旧版本操作被拒绝。普通流程保存通过 upsert 保留项目的来源关联。数据库连接、源日期/金额/项目校验或约束失败会回滚整单；批量操作中其他单据的成功结果不受影响。

部署时先执行迁移，再启动新版服务。此改动没有自动执行生产迁移或反向更新生产记录。

验证：`npm run check`。真实 PostgreSQL 回归测试使用显式指定的临时本地实例（测试会创建/删除自己的独立数据库，不读取应用 .env）：

```sh
RUNFENG_REFRESH_TEST_ADMIN_URL=postgresql://postgres:password@127.0.0.1:55439/postgres node --test test/legacyRefresh.integration.test.mjs
```
