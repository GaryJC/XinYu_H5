维修流程复查：修复 4 类问题

本轮检查单门店多人维修、配件准备、追加项目与返工轮次。重点核对状态变化、历史记录和重复请求。

1. 多人备料与开工范围不一致

原逻辑等待整份申请备齐才开工，共同申请又可能将其他尚无可用配件的维修工一并开工。用户已明确：本人部分配件备齐即可先做，其他维修工独立推进。

已修复：个人申请至少一项备齐即可开工；共同申请按已备齐明细的领料人启动对应项目。

其余明细继续显示待备料。后续备料不重写已有开工时间，个人暂停状态保留；改派接单保留原历史。完工提交仍要求本人及共同申请完整备齐；外包保留原规则。

位置：server/domain/dispatchPolicy.mjs、server/domain/partsRequirement.mjs

2. 下一轮新增项目复用了已删除项目的编号

新增项目使用负数编号。原返工逻辑只检查当前项目列表；删除过的最低编号已从列表消失，下一轮可能再次分配该编号，混淆新旧项目身份。

已修复：编号同时避开历史最低值、当前项目及待定项目，并保存新的最低值。

回归验证了“新增 → 删除 → 完工 → 下一轮新增”的完整顺序，数据库测试同时检查了历史轮次没有被改写。

位置：server/domain/repairRounds.mjs

3. 补充项目允许 200 字，提交完工只接受 100 字

超长名称可以成功发起下一轮维修，却在后续编辑或提交完工时被拒绝。

已修复：发起阶段的前后端都限制为 100 字，提前拦截超长输入。

100 字名称可完成接单和提检；101 字与 200 字在创建轮次前被拒绝。已有超长名称未自动截断，需显式修改。

后续只读核实：润丰名称字段已是 varchar(200)，按当前编码可容纳 100 个普通汉字；维修人仍为 varchar(100)。同步 SQL 残留的名称 100 字节校验与转换已修正为 200 字节。H5 的 100 字符限制与数据库的 200 字节限制是两个概念。

位置：server/domain/repairRounds.mjs、client/src/features/dispatch/DispatchActionDialog.tsx

4. 删除最后一个追加项目，工单卡在“维修中”

待结算工单新增项目后会重新进入维修。若随后删除所有未完工的追加项目，剩下的都是已检验项目，原逻辑仍停在“维修中”，无法继续提交，也无法正常收尾。

已修复：只剩已检验项目时恢复“维修完成”，同一事务内保存最终同步快照。

原有检验记录保持不变；剩余项目仍在维修或待检验时不会自动完工。重复请求不生成第二份同步任务。同步校验失败会记录为待处理错误，不阻止本地撤销。

位置：server/domain/dispatchPolicy.mjs、server/services/dispatchService.mjs
