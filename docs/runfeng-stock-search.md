# 按本车维修历史找件

仓管配件申请详情以派工号为突出显示的信息，支持一键复制。托修单位、车型、主修人、委托单号等其他详情默认折叠。派工号未回填时显示“待润丰回填”，不把 H5 委托单号当成润丰派工号复制。

## 所需配件整理

仓管可以新增、修改和删除当前未出库的配件，支持名称、数量和单位。全部删除时需要明确选择“无需配件”。已出库清单只读，原数量与交接记录不能被后续编辑覆盖。

仓管通过 `edit-parts` 动作保存，使用既有版本校验、事务、审计与请求幂等机制。修改会清除原备料结果，保留旧需求和备料事件，重新待备料，并通知维修工查看最新清单。选择无需配件的待开工任务可直接开工，维修参与人记为维修工，仓管不会被当作维修人员。

手写照片需求可由仓管整理成明细，原照片 ID 从既有需求继承为 `sourcePhotoIds`，不能由客户端伪造。请求重试对嵌套对象和配件数组做完整规范化比较；键顺序不同的同一内容可安全重试，改变内容仍被拒绝。

## 历史匹配逻辑

打开详情时，服务器使用工单自身车牌查询润丰该车以前的维修用料，不接受客户端另外指定车牌。首先展示上次实际登记的品名、货号、规格、单位、用量、维修日期和历史派工号。默认按当前第一项配件需求筛选，可以切换其他需求或查看全部本车历史型号；滤芯／滤清器仅作为本车历史列表的文字筛选同义词，不会引入其他车辆或全库型号。

只有选中本车历史中确实存在的货号，才按该货号精确查询当前配件档案和分仓结存。不会按“机油”等泛称自动改配其他型号。复制历史货号后可在润丰快速找件。历史用量单位与库存当前单位分别展示，不自动换算。

没有以往维修记录的新车显示“已跳过仓库匹配”，不请求配件档案或库存。已有维修但没有材料明细时也明确跳过。连接失败、未配置或车牌缺失显示错误，不能伪装成新车无历史。

## 数据来源和边界

- 历史维修头：`dbo.qxwxb`，按精确车牌匹配、排除当前派工号和删除记录，只使用正式账套 `wd=''`，避免另一账套的同号记录重复或混淆单位。
- 历史材料：`dbo.qxwxmxb`，按 `dh` 关联头记录，同时限定 `wd=''`、`lb='材料'` 和正数用量。`hh` 是当时品名，`hh0` 才是货号；规格读取 `gg`，厂家读取 `cd`，单位读取 `jldw`，用量读取 `sl`。使用历史快照，不以现行主数据覆盖当时型号。
- 当前档案与库存：`dbo.hpxxb`、`dbo.cskcb`、`dbo.bmxxb`。按历史货号精确查找，按部门、仓库、货位展示 `jcsl` 结存。未使用另一含义的 `dqkc` 字段。

最多读取最近 50 次维修和 500 条材料，展示 60 个历史型号，达到边界会提示。相同货号、规格、厂家、单位保留最近一次维修记录，仅累加该次维修的同类明细；不同单位、不同规格不会合并。没有货号的历史记录仍显示原型号，但不能据此猜测库存货号。

本功能只读润丰，无库存预留、库存扣减或自动出库。实际备料和出库由仓管在润丰核对办理。无需新增表结构或迁移，JSON 和事件保存新增整理字段。

## 接口与权限

- `GET /api/dispatch/tasks/:orderId/parts-history`：本车以前维修使用过的型号。
- `GET /api/dispatch/tasks/:orderId/parts-history/stock?code=...`：校验货号确实属于本车历史后，精确查库存。
- `POST /api/dispatch/tasks/:orderId/actions`，`action: edit-parts`：仓管整理需求。

历史和库存查询仅有效仓管、管理员可用，沿用本店已签字任务访问权限。整理需求仅仓管可执行，并须任务已接单且处于待开工、维修中或暂停。原 `/parts-stock` 及 `/parts-stock/warehouses` 只读接口保留兼容，仓管默认流程已改为上述本车历史匹配。

验证覆盖同车牌历史、当前维修排除、正式账套、规格和单位保留、新车跳过、历史原货号限制、仓管增删改、备料失效、已出库保护、版本冲突、幂等重试和 HTTP 权限；另以只读查询验证真实润丰历史及新车无历史路径。运行 `npm run check` 及隔离临时数据库集成测试。
