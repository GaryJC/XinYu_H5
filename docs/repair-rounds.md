# 完工后返工

管理员或服务顾问在本店已维修完成的任务详情点击“发起返工”，支持待结算及已完结工单。选择原项目和／或添加补充项目，填写原因、新完工时间及派工安排后通知处理人接单。原委托单、客户签字和单号复用；无新增收费或平台同步。

返工以独立轮次保存；`dispatch_tasks` 提供当前轮次投影，`dispatch_repair_rounds` 保存原始维修及各次返工快照。关闭的轮次不再更新，后续轮次可选择之前的补充项目。原 `repair_items`、原工时、费用和结算记录保留。首次归档旧任务时不补造未知时间。新补充项目使用当前工单内不重复的负数项目标识。

复用 `/api/dispatch/tasks/:id/actions`，增加 `reopen-repair` 动作以及 `reworkItemIds`、`additionalItems`；保留版本号及幂等请求编号。详情新增 `repairRounds` 和可选原项目目录。照片上传携带 `repairRound`，省略只适用于原始维修；服务器锁定工单后校验轮次、人员和状态，照片按轮次归档。

返工期间，已完结单的商业状态仍为“完成”，派工列表以当前维修阶段呈现；待结算单同样保留商业状态，但服务端阻止返工期间最终完结及结算。检验通过后恢复原结算流程。原工时缺失时，返工结束后可通过现有入口补录原单工时；不单独统计返工工时。完成量仍按当前工单去重，不把轮次叠加成工单数。

迁移：`202610150003_repair_rounds.sql`。仅本地开发数据库已应用；正式环境需要在启动新服务前按现有迁移流程应用。当前调度通知与临期提醒的未提交改动继续保留；临期去重键加入维修轮次，防止前一轮提醒影响下一轮。

验证：`npm run check`；设置指向本机 PostgreSQL 的 `REPAIR_ROUNDS_TEST_ADMIN_URL` 后运行 `node --test test/repairRounds.integration.test.mjs`，测试创建并清理独立数据库。另运行原有 `dispatch.integration.test.mjs` 回归派工、照片、检验和通知。页面在 375、390、430、1280px 验证；真实钉钉相机、相册、软键盘及正式通知需真机验收，本地仅使用 mock。
