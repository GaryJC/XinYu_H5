P2 追加维修被退回后，漏进返工分类

来源：server/domain/dispatchTaskFilters.mjs:47，同样判断还出现在该文件 73 行和 server/domain/dispatchTaskSort.mjs:14。

检验拒绝会把任务设为 rework=true 并填入 rejectedItemIds，但不会把原来的 roundKind=additional 改掉。当前分类只要看到追加轮次，就忽略真正的退回返工标记。

复现：通过实际 applyDispatchAction(...inspect...) 退回追加轮次项目，得到维修中、rework=true、rejectedItemIds=[1]，随后查询返工分类返回 0 张。待处理中的返工优先级也丢失。

建议：区分“普通追加维修”和“追加维修被检验退回”。先识别实际退回，再考虑轮次类型；让列表、计数、排序共用同一规则。添加从追加维修→提检→退回的回归用例。

P2 多人单将同事的返工算到本人

来源：server/domain/dispatchTaskFilters.mjs:35–47；排序的返工优先级也取整单字段。

代码已按本人项目换算状态，但保留整单的 rework 和 rejectedItemIds。A 的项目被退回，B 的项目还在正常维修时，B 也会在个人返工分类看到该单。

复现：对多人任务执行实际检验动作，仅退回 A 的项目 1；B 的项目 2 仍为维修中。以 B 身份查询返工，结果为 1 张，而 B 没有被退回的项目。

建议：个人分类和优先级结合本人负责项目与退回项目的交集；明确整轮返工、当前项目退回和历史退回的范围，保留必要的旧数据兼容。加上 A 退回/B 正常、B 已通过、返工项目重新分配等测试。该修正不等于移除返工在普通状态分类里的显示，不涉及用户已撤回的互斥分类调整。

性能清理建议：详情仍加载未使用的列表和计数

TechnicianProjectDetail.tsx:11 复用完整 useDispatchController，打开完工核对详情也会加载不可见的任务列表与 myCounts；控制器每 30 秒继续刷新。全项目搜索发现 taskCounts 没有界面消费方。myCounts 和列表分别调用 listDispatchTasks，产生额外查询与处理。

建议拆出详情控制器或增加列表/计数开关，删除无消费者的计数请求。这里只确认了调用路径，没有做大数据量延迟测量，因此未将其列为已量化的性能故障。
