单门店流程复查：修复 4 类问题

本轮重点检查派工请求、待确认项目和相关数据校验。按要求暂不扩展跨店功能，保留原有隔离检查。

1. 请求超时后重试，可能重复执行

后端已经完成操作，但客户端收到 502、504 等错误时，原逻辑会丢弃请求编号。用户重试生成新编号，可能再次执行催办等操作。

已修复：模糊失败保留原请求编号、请求内容和版本号；明确拒绝后才生成新请求。

回归覆盖 HTTP 408、500、502、503、504，以及版本冲突后使用最新数据重试。

位置：client/src/features/dispatch/useDispatchController.ts

2. 请求编号生成失败，派工操作一直忙碌

编号生成发生在异常处理之外。WebView 随机数接口异常时，操作状态无法复位，后续点击均被拦截。

已修复：将编号生成纳入异常处理，显示错误并释放操作锁，允许重试。

位置：client/src/features/dispatch/useDispatchController.ts

3. 待确认名称允许过长，后续流程拒绝

登记允许 200 字，正式维修项目与本地写回校验只允许 100 字；待定写回还会添加“【待定】”前缀。

已修复：前后端共用 96 字上限，预留前缀空间，在登记时阻止超长内容。

验证了 96 字边界能进入维修编辑、加前缀后通过本地快照校验，以及超长登记和草稿修改被拒绝。

位置：shared/pendingRepairLimits.mjs、server/domain/pendingRepairs.mjs、待确认项目组件。

4. 重复项目编号与异常行可破坏草稿数据

重复编号可保存为两条指向同一维修项目的确认记录；空值行触发 500，而非输入校验错误。

已修复：保存前校验行结构和编号唯一性；拒绝时保留原记录与版本。

同名但编号不同的项目仍可分别保存，确认历史互不覆盖。

位置：server/repositories/pendingRepairsRepository.mjs
