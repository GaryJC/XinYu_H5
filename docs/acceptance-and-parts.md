# 接单、备料与出库开工

需要配件的流程：维修工接单并登记需求 → 待开工 → 仓管备料完成 → 通知维修工领取 → 仓管实际交接时确认出库 → 自动进入维修中。无需配件的任务接单后直接开工。

维修工在接单时选择“无需配件”“填写配件”或“清单照片”，支持快捷配件、手填数量单位和拍照／相册。维修单和配件进度分别展示：维修任务使用既有“待开工”阶段；配件显示待备料、待领取、已出库。

仓管先按本车车牌查以往维修使用过的型号，再按历史原货号查询库存；新车无历史时跳过匹配。派工号突出显示并可复制，其他委托单详情默认折叠，仓管可增删改未出库需求，详见 [润丰仓库检索](runfeng-stock-search.md)。

## 仓管操作

仓管只能处理本店、已接单且处于待开工／维修中／暂停的配件需求。仓管页面按待备料、待领取、已出库、全部记录筛选，支持搜索车牌、委托单号和派工号。

“备料完成并通知领取”记录真实仓管、时间，并向当前维修工加入钉钉通知队列；外包任务通知本店有效服务顾问和管理员。维修工看到“配件已备齐，请到仓库领取”。此时仍为待开工。

当面交接时点击“确认出库”，核对领取人及本次配件全部交接后确认。系统在同一事务内保存出库人、领取人、时间、完整清单和事件，将待开工任务及项目转入维修中，记录实际开工时间。维修工无需再次点击“已领取”。仓管不会被记录为维修参与人，已通过项目和已有开工时间保持原记录。

暂停任务允许备料、出库，但保持暂停；如果暂停前为待开工，出库后恢复目标变为维修中。未出库需求阻止开工和提检，旧版逐项及整单接口同样校验。没有配件需求字段的历史任务保留旧流程。

本次出库是应用内的配件交接记录，保存在现有任务 JSON 和不可改写的派工事件中；不扣减库存、不调用外部库存系统，也不使用旧版按维修项目生成的模拟出库单。照片清单整体确认交接，未引入部分出库流程。

## 修改与追加

未出库需求可以修改。修改会清除本批备料结果并重新通知仓库；旧清单和备料记录保留在事件历史中。备料后的改动也必须重新备料，不能直接出库。待开工需求改成“无需配件”后直接开工。

已出库后入口变为“追加配件申请”，表单从空白开始，只填写本次新增需求。每个新批次单独备料、出库，维修单继续处于维修中，保留原开工时间；本次新增配件未出库前不能提检。原已出库数量保留在事件中，不能通过编辑新批次覆盖。退料、部分出库及库存台账不在本次实现范围内。

清单照片可勾选用于本次申请的照片，追加申请不会自动重复携带上批照片。服务器校验照片必须属于本单、本轮维修且类型为 `repair_parts_photo`。失败上传沿用原请求编号重试。

## API、历史与通知

保持原 API 路径。`accept` 保存必填配件需求；`record-parts` 修改未出库需求或登记新批次；`edit-parts` 供仓管整理尚未出库的需求；`confirm-parts` 更新为备料完成；新增 `issue-parts` 确认出库。所有操作沿用任务版本、当前角色校验、数据库事务和请求幂等机制。

`partsRequirement` 增加 `sourcePhotoIds`、`revision`、`batch`、`prepared*`、`issued*`、`recipientIds`、`recipientName`，任务、事件及维修轮次快照都保存需求。旧 `confirmed*` 仅表示历史申请确认，不被解释成备料完成或已出库。本次扩展现有 JSON，不更改数据库表结构，无新增迁移；现有配件照片和仓管角色迁移仍需已应用。

钉钉通知沿用既有队列和 `DISPATCH_NOTIFICATION_MODE` 配置。领取／出库通知发送前再次核对门店、有效角色、当前维修工、维修轮次、需求时间与修订号及配件进度，过时通知取消；发送结果未知时沿用原查询机制，避免盲目重发。通知失败不撤销已经完成的业务操作。

新一轮返工重新登记需求，不继承上一轮配件状态。维修照片与清单照片分开，提交完工仍须至少一张本轮维修过程照片；已有接车照片、派工单、费用、签字和结算继续使用原流程。

## 验证

运行 `npm run check`；数据库集成测试使用显式 `DISPATCH_TEST_ADMIN_URL` 创建独立临时库，覆盖迁移、并发备料／出库、幂等重试、修改后备料失效、通知和追加历史，不修改业务库。正式钉钉消息送达、相机与 WebView 仍需在真实设备验收。
