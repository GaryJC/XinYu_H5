## 验收口径

目标是覆盖当前可识别的全部业务模块、状态转换、角色边界、外部同步与故障恢复。无限输入及所有组合无法穷举；通过模块清单、状态乘积矩阵、边界分区和高风险组合补齐覆盖，并把无法验证的外部消费者行为记录为阻塞，不能算通过。

业务预期优先采用用户已确认规则，其次为最新业务约定；代码用于找实现和分支，不能充当唯一正确性标准。旧文档与新实现有冲突时必须记录，不通过修改预期使测试变绿。

P0：错单、丢数据、越权、重复写入、资金工时被覆盖、主流程阻断。P1：重要分支、恢复能力、设备兼容及展示准确性。视觉细节作为P2探索项，不替代P0/P1验收。

每条用例均执行「准备前置数据 → 按表操作 → 检查界面和接口 → 比较数据库前后差异 → 检查审计及异步任务」。表中列出的多个状态、角色、字段或边界值必须展开为独立执行子用例，例如 WRITE-005.gs.negative.external，不能只测其中一个就勾选整行。

## 状态与权限的系统性覆盖

对 `dispatchPolicy.mjs` 中每个动作建立「动作 × 源状态 × 角色 × 归属 × 版本」表：assign、reassign、reoffer、cancel、accept、decline、start、finish、pick、start-order、submit-order、submit、pause、resume、inspect、claim-inspection、reassign-inspection、update、update-technicians、update-due、edit-repair-items、record-parts、edit-parts、confirm-parts、issue-parts、reopen-repair、send-review、submit-review、record-hours、remind、retry-notification、retry-inspection-notifications、retry-scheduler-notifications、reconcile。执行前从源码重新核对动作表，新增项自动列为覆盖缺口。

源状态包含：草稿、待客户签字、待处理纸质委托书、已委托、待派工、待接单、待开工、维修中、暂停、回审、待检验、维修完成、待结算、完成。工单商业状态、派工阶段、个人项目状态、待确认决定、配件状态、同步队列状态分别建表，不把不同层级名称混成一条状态链。

每个合法转换至少覆盖成功、错误角色、跨店、非本人、停用、旧版本、重复请求；每个非法源状态至少一条API拒绝测试。多角色只扩大允许业务能力，不能绕过自检限制。待确认安排权限与照片/四项更正权限不能共用「必须原负责人」假设。

高风险组合完整展开：金额字段×正负零NULL×内外账；检验结果×待定决定×维修轮次×写回结果；个人申请×部分备料×个人提交；领取/提交/ACK各断点×重启/重复消费。低风险展示选项采用两两组合并保留组合清单。

## 执行顺序和验证方式

1. 固化基线、数据字典、状态权限表，处理D02/D04待确认口径；建立独立测试数据库和测试身份。
2. E1运行领域、API权限、事务集成测试；核对每条计划编号与具体测试名称，不把文件存在计为覆盖。
3. 执行P0浏览器主流程，再执行全部P1和多设备测试；首次失败保留现场，不边测边改代码。
4. E2执行SQL保护及故障注入；E3执行真实消费者、钉钉和润丰客户端核对。某环境不可用则标记阻塞，不用mock结果代替。
5. 执行并发、容量、迁移和恢复；汇总缺陷及业务决策，不自动修复、发布或推送。

## 证据与缺陷记录

每个展开子用例填写：编号、版本/环境、数据ID、角色、前置快照、具体步骤、预期、实际、开始结束时间、接口结果、数据库差异、截图/录屏、日志关联ID、异步等待窗口、通过/失败/阻塞/待确认、缺陷ID。成功标准既看应发生变化，也看签名、历史轮次、非项目费用等不应改变的数据。

每项缺陷记录最短复现步骤、影响范围、严重度、是否已有生产事实、疑似原因与已证实原因的区别；本阶段不执行修复。故障注入后的恢复只是测试步骤，不等同授权修改生产故障。

建议证据目录为 `output/system-test/<run-id>/<case-id>/`，报告不保存凭据、签字原图或完整客户隐私。跨系统用orderId、eventId、jobId、repairRound关联证据，不仅凭提示文字判断成功。
