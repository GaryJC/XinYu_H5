# 我的事项与超时提醒

统一入口仍是顶部铃铛，打开后默认“待我处理”。“我在跟进”收纳本人提交后等待别人审批的出车申请；“通知记录”默认未读结果，“全部”保留历史业务通知。角标为待处理事项数＋未读结果数。已读不等于办结，只有业务状态变化才移除待办。首次催促、升级和每日汇总更新同一张卡，展开可查看提醒历史及相关事件。

## 规则

全部时间按北京时间，每天08:00–18:00计时与发送（含周末，无节假日日历）。夜间暂停，17:30开始的1小时待办在次日08:30达到阈值；恰在18:00达到阈值则次日08:00发送。扫描频率5分钟，实际发送还需加队列处理时间。

|类型|首次阈值|接收人|
|---|---|---|
|出车待审批|1工作小时|本店管理员，排除申请人|
|无维修照片待审批|1工作小时|有权审批的本店顾问/管理员，排除申请人|
|待派工|1工作小时|本单服务顾问|
|待客户签字/签字待确认|2工作小时|本单服务顾问|
|待检验|1工作小时|已领取则领取检验员，未领取则有检验权限的检验员|
|纸质委托书待同步|30工作分钟|首次仅本单顾问|

首次提醒入队后再过2工作小时仍未处理，通知原处理人并加入本店管理员；审批仍不能发给申请人本人。此后每天08:00的汇总回到实际处理人。没有有效接收人时不消耗提醒阶段，5工作分钟后重查。纸质同步明确失败在工作时间内尽快提醒本单顾问，既有重试不重置原始等待时间。未处理纸质委托书（尚未选择创建方式）不等同于待同步，不在此自动提醒范围。采购待审批保留在待办，但不在本轮超时催办范围。

## 历史与一致性

迁移 `202611150001_personal_pending_reminders.sql` 是新计时启用边界。所有现存状态只建立不催办基线，不回填古老开始时间、不补发、不纳入每日催办汇总。迁移后业务真正进入新状态、重新提检或新申请才创建可提醒的新轮次。编辑、领取检验、刷新、同步重试不会重置当前轮次。

业务事务提交时通过延迟触发器保存最终状态快照。独立投影器关闭旧状态、建立新状态；同一事务内中间状态不算新一轮。多人提检按项目/维修轮次跟踪，显示与摘要按工单/待办种类合并。同门店接收人、当前岗位、事项状态在发送前重新验证；撤销、完成和续保无关的新业务变更不复活旧提醒。原有预计完工48/24/1小时通知仍停用。

## 运维与性能

先应用001状态迁移及002准备租约迁移，再发布前后端。`DISPATCH_NOTIFICATION_MODE=disabled` 停止发送；投影仍执行以供事项页面使用。本地为mock，不代表真实钉钉送达。已有API路径保留，`/api/personal-workbench`增加待办/跟进计数与历史字段，`/api/inbox?results=true`仅取结果通知；`?personalTasks=true`直达统一入口。

状态投影每30秒处理最多10批、每批100事件，完成即删除事件；扫描待提醒索引每5分钟最多10批，若仍积压则下次继续，清空到期待办后再合并发送。每次循环最多10名接收人，一名接收人的待发送记录合成一份摘要，正文最多8项并给出总数；多项目同单同类合并。无新增客户端轮询频率，仍为可见页面30秒更新；消息列表仅通知页可见时读取，只有展开事项页才装载提醒历史。角标新增实际待办计数查询，需监控大门店查询耗时，未声称生产性能实测。

准备阶段保留pending并持有90秒租约，崩溃后可重新领取；封批核对租约后才持久化为unknown，不在HTTP等待期间持有数据库事务。开始发送后崩溃/结果不确定不自动重发；过期worker不能封批或覆盖后来领取者的结果。明确发送前校验异常可稍后重试。每阶段/每日/接收人有唯一约束。实际钉钉HTTP尝试记入既有用量统计，来源pending-reminder，不自动付费查询送达结果。

发布后观察投影积压、到期待提醒数量、统计请求耗时及通知调用量。回滚代码时保留新迁移，避免丢失历史分界、轮次和发送去重记录。
