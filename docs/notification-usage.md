# 钉钉工作通知调用追踪

管理员进入「数据看板」，展开「钉钉通知用量」。面板提供按日发送/查询次数、近七日完整日期平均值、通知类型和收件人分布，以及每页 50 条调用记录。每日 300 次为参考预算，不是自动停发阈值。

## 统计口径

- 只统计本应用、本店的工作通知发送与人工结果查询尝试，覆盖派工、采购、车辆申请、历史行驶证备案、保险提醒五类来源。不是企业所有应用的账单。
- 在实际 fetch 前创建唯一追踪编号。再次实际调用会产生新编号，通知编号、事件编号和业务编号用于识别同一消息重试、同一事件的多人收件及关联工单。
- 模拟发送、已停用通知、取凭证失败及尚未发请求的参数校验失败不计入。HTTP/业务拒绝、连接超时等已经尝试的调用计入；实际是否抵达平台、是否计费以钉钉后台为准。
- “调用成功”只表示 API 请求成功；发送接口成功受理不等于员工已收到或已读，不改变原通知业务状态。
- 只从部署迁移后首次真实调用开始记录，不补造历史。中国时区自然日统计，首次记录当天和当前日标为“部分”，不参与完整日均；完整的零调用日期参与平均。
- 记录开始后进程退出或完成记录写入失败，会留下“中断待确认”，不能据此自动重发。记录开始写入失败则数据库可能漏计，服务日志仍保留追踪编号；面板不是财务账单。

## 排查方式

1. 先看某日发送与查询拆分，再看通知类型和收件人分布。
2. 在明细复制追踪编号；服务端日志搜索 `[dingtalk-call]` 及该编号，可关联开始和结束。
3. 同事件多人收件会有相同事件编号；同通知重复尝试会有相同通知编号、不同追踪编号。采购旧数据没有批次编号时，事件编号回退为通知编号，不推测合并关系。
4. `[dingtalk-trace-write-failed]` 表示记录不完整，需要检查数据库；不会因为追踪失败自动重发通知。

## 权限、性能与发布

- GET `/api/notifications/usage?date=YYYY-MM-DD&page=1` 每次重新核对当前员工启用状态、管理员角色和门店；仅返回本店记录。两张追踪表启用 RLS，客户端不直连读取。
- 不保存凭据、钉钉账号、通知正文或客户内容。记录保留业务标识、收件人内部编号/姓名、分类和调用结果；服务日志不包含收件人姓名或通知正文。
- 面板默认收起，没有轮询；打开、翻页或刷新才读本地数据库。切换身份取消请求并清空数据，不新增任何远程 OpenAPI 调用。
- 每次实际 API 尝试增加一次开始 INSERT 和一次结束 UPDATE，单条客户端查询超时 500 ms；数据库连接等待沿用共享连接池的 5 秒设置，不能把 SQL 超时当成整个记录操作的绝对耗时上限。记录失败后继续原通知流程，不重放请求。
- 本地隔离 PostgreSQL 测得两次写入合计约 1 ms 量级；不是线上端到端开销保证。新增 `(shop_id, started_at, id)` 索引；目前没有自动清理历史的任务。
- 发布需要先应用 `202611110003_notification_call_traces.sql`（以及前序未应用迁移）。迁移与本轮代码当前仅本地验收，未部署。

300 次/日约为 9,000 次/30 天，但这不能保证本月剩余额度够用：历史已消耗额度不会减少，企业其他应用仍可能消耗额度。


## 多人合并发送（2026-11-11）

- 派工、采购、出车三个仍在使用的投递入口接入持久化批次；已经停用的保险、行驶证及其他通知保持停用。后台仍按原5秒间隔处理，不为凑批额外等待。
- 只领取到期pending，准备阶段保留pending并加90秒租约；此时进程中断可在租约到期后重新领取。封批事务才转unknown，因此已可能发出的消息不会自动重放。领取时清除本次重试的旧task/batch/账号关联，历史批次和成员快照仍保留。同一来源/业务/事件才是候选，派工还要求同kind和维修轮次；无可靠事件标识的历史记录按原单条处理。候选上限20人，超出的下一轮处理；最终按完整消息内容（含标题、链接、应用编号）分组。
- 每人沿用原有岗位、项目、维修轮次、检验/配件/用车状态检查；内容生成后，实际发送前再次逐人复核。封批事务核对租约、启用状态、所属门店和实际钉钉账号。内容或绑定变化的成员重新排队复核，不带入本次请求。
- 009迁移新增批次、成员快照表，以及通知/调用记录的批次关联。收件人快照在网络前持久化，同一账号去重传入userid_list；每位员工独立通知记录保留。网络请求不持有数据库行锁，超时/连接中断/落库失败不自动重放已尝试发送。
- 同一批成员共用task_id。手动查询按批次取得90秒租约及30秒间隔，调用一次getsendresult后逐人判断结果；失败者与成功者分开保存。查询使用发送时账号；某人重试进入新批次，旧批次结果不能覆盖新消息。关闭自动结果查询的策略不变。
- 用量按实际HTTP尝试计数。3人一批的发送只计1次；收件人分布显示关联次数，不能将各收件人次数相加当作API总量。明细可查看批次编号和人数；不把平台受理解释为全员收到。
- 每批新增两段短事务保存批次及结果，仍有逐人业务复核SQL。小样本本地三人准备/持久化约8～9ms（模拟网络，不是生产P95）；主要收益为减少远程调用。范围为同消息多人合并，不取消任何额外通知，也不承诺日均必定低于300。
- 本次已经在实际本地mock开发库补齐001/002/004/005/006及009迁移；生产未应用、未部署。真实钉钉投递与线上降幅尚未实测。
