# 整单维修、过程照片与检验领取

维修工使用“我的维修”的待接单、进行中、待检验、已完成分类。确认接单时登记配件需求，接单即进入维修中，不再单独点击开工。暂停和无法接单直接显示在操作栏。检验退回只处理退回项目；完工后返工由本店服务顾问或管理员发起。配件登记与派工单信息详见 `acceptance-and-parts.md`。

提交完工前必须至少上传一张当前维修轮次的过程照片（整单及旧版提检入口均在服务端校验），与接车照片及配件清单照片分开，成功上传后即归档，不提供删除入口。上传使用 `/api/dispatch/tasks/:orderId/photos`，需请求编号、文件名、图片 MIME 和 Base64。仅当前本店维修工，或本店外包任务的管理员／服务顾问，可在待开工、维修中或暂停状态上传；同一个请求编号重试返回同一照片。允许 JPEG、PNG、WebP，单张不超过 8MB。相机／相册复用现有 WebView 文件选择与图片压缩。

整单动作通过现有 `/api/dispatch/tasks/:orderId/actions` 接口执行：`start-order`、`submit-order`、`claim-inspection`、`reassign-inspection`、`retry-inspection-notifications`。版本校验、工单行锁和请求编号防止并发领取及重复操作。旧逐项目动作和已指定检验员的历史任务继续可用。

提交完工先保存待检验状态和后台通知解析任务，再由通知 worker 处理角色同步和逐人通知。新队列不要求维修工选择检验员；合资格检验员先领取，再提交检验结果。管理员重新分配须说明原因。同步或通知失败不会撤销维修工的提交，在调度详情中展示错误并提供重试。

运行前应用新迁移：`npm run migrate`。迁移增加维修过程照片类型、照片请求去重索引、检验通知解析队列及钉钉检验员成员状态，不改动已应用的迁移。

- 本地 `DISPATCH_NOTIFICATION_MODE=mock` 使用本店开发检验员模拟通知，不请求钉钉。
- 正式 `DISPATCH_NOTIFICATION_MODE=dingtalk` 需要已有应用通知配置和通讯录角色、成员、用户详情读取授权。完整分页读取“检验员”角色，同步全部角色，包括兼任服务顾问等角色的检验员；角色优先级仅决定默认首页。新员工按当前单门店约定归入工单门店；已有员工保留门店与停用状态。
- 正式同步失败不会静默使用本地人员替代。已移出角色的绑定人员不再成为通知对象或领取人；管理员原有协助检验权限保留。
- 不发送尚未明确成功的通知请求第二次；明确失败的发送记录可由调度重试。检验员解析队列可重试，发送任务按事件、接收人及类型去重。

验证包括 `npm run check`，以及显式提供本地 `DISPATCH_TEST_ADMIN_URL` 的隔离 PostgreSQL 集成测试。测试数据库独立创建并清理，不使用应用工单。真实钉钉推送、手机相机／相册、软键盘和安全区仍需设备验收。

## 派工通知与临期提醒

- 拒绝接单、暂停维修、提交检验均通知本店全部有效服务顾问及管理员。正式模式后台完整读取钉钉角色成员，覆盖尚未登录的员工，保留已有门店归属和停用状态；模拟模式使用本店开发员工。
- 调度通知包含车牌、维修内容、操作人、原因／提检说明和预计完工时间；角色同步失败不撤销维修动作，派工详情显示错误并支持重试。每个业务事件、接收人及通知类型只创建一条发送任务。
- 后台每分钟扫描临期任务，按预计完工前 **48小时、24小时、1小时** 三档通知当前维修工。每档对同一工单、同一截止时间和同一维修工仅生成一次。实际投递还取决于后台队列和钉钉处理时间。
- 当前剩余时间在24至48小时内使用两天档，1至24小时内使用一天档，最后1小时使用一小时档；新建或改期时错过的档位不补发，避免多条通知一起到达。
- 待接单、待开工、维修中及暂停可提醒；拒单待处理、已提检、维修完成、未签字、历史待核对、外包和已超期任务不生成临期提醒。多人协作通知所有当前有效维修工。
- 改期后按新截止时间计算，改派后的新责任人可收到当前档提醒。真正发送前再次核对截止时间、档位、状态及维修人员；旧提醒失效后不再发送。系统提醒事件使用系统身份，不冒用维修工操作记录。
- 新增迁移 `202610150001_dispatch_notifications_and_due_reminders.sql` 创建调度通知解析队列和临期去重记录。当前本地仍为 mock，不代表真实钉钉推送已验收。

派工单信息中展示已有接车／车损照片，维修工可点击放大查看；复用本单、本店及当前指派人员的读取权限，不包含行驶证与签字照片。

检验全部通过时由实际检验人必填本轮工时（大于 0、最多两位小数），随检验动作在同一事务内保存工时、记录人和时间；有退回项目时不录工时。管理员／服务顾问不再单独录入工时。历史已完成但缺失工时的任务，仅本单检验人可补录；已有工时不允许用补录入口覆盖。返工新轮次重新登记工时，原始轮次工时保留在历史快照中，原单最终完结仍核验原始维修的工时。手写清单照片选择后自动上传并选用，无需逐张确认。

## 检验单回审

待检验、已检验但尚未完结的工单，可由独立检验员或管理员在检验单中点击“发送回审”。工单进入“回审”分类，沿用原维修工、配件和维修照片；原检验结果保留在操作记录中。维修工在原维修详情中编辑本人项目，底部点击“提交回审”，随后重新进入待检验，按原流程领取并检验。多人任务须全部维修工分别提交完成后才进入待检验。

发送回审会向维修工推送钉钉工作通知（附说明及工单链接）；全部提交后，向合资格检验员和服务顾问/管理员推送待处理通知。使用现有通知队列、失败重试和幂等机制。上线前需执行迁移 `202610220002_repair_review.sql`。

### 配件申请附图

在“填写配件”里可选填最多 10 张配件照片，复用现有照片图库的拍照、相册多选、替换、管理和删除所选操作。照片上传中不能发送申请；失败项可重试或移除。配件照片通过 `PartsRequirement.referencePhotoIds` 随申请提交，仓管在所需配件和历史记录中查看；移除照片后提交才更新当前申请，历史申请保留原附图。配件实物照片与“清单照片”的手写清单用途分别保存，不影响文字配件明细及分项备料。
