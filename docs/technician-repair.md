# 整单维修、过程照片与检验领取

维修工使用“我的维修”的待接单、进行中、待检验、已完成分类。主要操作为接单、整单开工和提交完工；暂停和无法接单位于“遇到问题”。返工仅重开尚未通过的项目。

维修过程照片是选填记录，与接车照片分开，成功上传后即归档，不提供删除入口。上传使用 `/api/dispatch/tasks/:orderId/photos`，需请求编号、文件名、图片 MIME 和 Base64。仅当前本店维修工可在待开工、维修中或暂停状态上传；同一个请求编号重试返回同一照片。允许 JPEG、PNG、WebP，单张不超过 8MB。相机／相册复用现有 WebView 文件选择与图片压缩。

整单动作通过现有 `/api/dispatch/tasks/:orderId/actions` 接口执行：`start-order`、`submit-order`、`claim-inspection`、`reassign-inspection`、`retry-inspection-notifications`。版本校验、工单行锁和请求编号防止并发领取及重复操作。旧逐项目动作和已指定检验员的历史任务继续可用。

提交完工先保存待检验状态和后台通知解析任务，再由通知 worker 处理角色同步和逐人通知。新队列不要求维修工选择检验员；合资格检验员先领取，再提交检验结果。管理员重新分配须说明原因。同步或通知失败不会撤销维修工的提交，在调度详情中展示错误并提供重试。

运行前应用新迁移：`npm run migrate`。迁移增加维修过程照片类型、照片请求去重索引、检验通知解析队列及钉钉检验员成员状态，不改动已应用的迁移。

- 本地 `DISPATCH_NOTIFICATION_MODE=mock` 使用本店开发检验员模拟通知，不请求钉钉。
- 正式 `DISPATCH_NOTIFICATION_MODE=dingtalk` 需要已有应用通知配置和通讯录角色、成员、用户详情读取授权。完整分页读取“检验员”角色，沿用现有角色优先级映射。新员工按当前单门店约定归入工单门店；已有员工保留门店与停用状态。
- 正式同步失败不会静默使用本地人员替代。已移出角色的绑定人员不再成为通知对象或领取人；管理员原有协助检验权限保留。
- 不发送尚未明确成功的通知请求第二次；明确失败的发送记录可由调度重试。检验员解析队列可重试，发送任务按事件、接收人及类型去重。

验证包括 `npm run check`，以及显式提供本地 `DISPATCH_TEST_ADMIN_URL` 的隔离 PostgreSQL 集成测试。测试数据库独立创建并清理，不使用应用工单。真实钉钉推送、手机相机／相册、软键盘和安全区仍需设备验收。
