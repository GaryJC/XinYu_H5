# 维修派工与人员进度管理

客户签字后的委托单可以整单指派给一名或多名平级维修员工，也可选择外修（员工外派）或外包，不等待润丰派工号或出库单。维修工确认接单后按项目开工、提报完成，指定检验员或管理员检验；全部通过后才进入待结算。服务顾问与管理员在派工台和维修工详情中调度、查看负荷。

## 上线配置

1. 备份数据库，并执行 `npm run check`。在目标环境使用现有迁移流程应用 `202609110001_dispatch_management.sql`，再更新服务端和前端。历史迁移不需要重跑。
2. 在“权限设置”的钉钉角色映射中配置服务顾问 `advisor`、维修工 `technician`、检验员 `inspector` 的钉钉角色 ID、角色名称及门店 ID。员工进入应用登录一次后出现于人员名单。多个角色优先级为管理员、服务顾问、检验员、维修工。既有服务顾问/门店管理员按名称映射继续有效，明确禁用的角色映射不会回退启用。
3. 钉钉应用必须有工作通知发送权限，收件人在应用可见范围中。服务端配置 `DINGTALK_APP_KEY`、`DINGTALK_APP_SECRET`、`DINGTALK_AGENT_ID`、`DISPATCH_APP_URL`（HTTP 或 HTTPS 应用地址）。这些值不进入前端或 Git。
4. `DISPATCH_NOTIFICATION_MODE=disabled` 是明确的默认值：通知持久化排队但不发送。开发或测试设置 `APP_ENV=development/test` 和 `DISPATCH_NOTIFICATION_MODE=mock`，模拟平台受理和发送成功。生产配置完成后设置 `DISPATCH_NOTIFICATION_MODE=dingtalk` 并重启服务；此前积压的通知也会开始处理，启用前先核对积压。
5. 先验证一个门店的各岗位登录、手机/PC 深链、消息和数量看板，再逐步推广。真实消息联调需明确指定收件人。生产从不自动回退模拟发送。

独立通知 worker 随 API 进程启动，每五秒领取任务，使用数据库租约与 `SKIP LOCKED` 支持多实例。部署时先迁移；停机等待本进程发送结束再关闭数据库连接。

## 日常操作与统计口径

- 首次派工需要选择维修员工（外包填写承包方及施工方式）和预计完工时间，可加急或备注。无法接单必须填写原因，原任务保留，调度人员可以重新发起接单、改派或撤销未开工任务。
- 改派保留原项目进度与操作人，新维修工重新接单后继续。开工后必须填写交接说明，不能撤销；待检验和维修完成任务不直接改派。
- 暂停原因包括待配件、待客户确认、技术问题、其他；恢复返回原阶段，不自动顺延预计完工时间。领料是领取记录，不影响开工资格，也不代表真实库存扣减。
- 提报前全部项目必须完成。检验可全部通过，也可勾选项目退回并填写原因；其余本次项目通过。维修工本人及参与过该任务项目操作的人员不能自检，管理员代检也留痕。
- 待接单包含改派后的接单确认；尚未开工包含其中从未开工的任务，两者有重叠。维修中、暂停、待检验分别显示；超期和返工是可重叠标记，各列不可相加。
- 当前任务数不受历史日期筛选影响。完成量按上海时区的检验通过时间统计，默认本月，按最终维修员工名单计算个人参与完成量，同一工单只在工单列表计一次，不能将多人的参与量相加作为整店完成量，与是否结算无关。所有数量可点击查看明细。
- 历史记录只在同店同名人员唯一时关联 ID。无法判断人员/进度的任务需要管理员核对；不补造历史开工、接单、完成时间，不因迁移补发消息。无完成日期的历史完成记录只能在“维修完成”阶段查看，不计入日期范围完成量。

## 通知运维

新派工和重新接单通知全部所选维修员工；改派通知新、原员工；撤销通知原员工。外包任务的通知发给同店在职服务顾问和管理员，由其录入进度。无法接单通知原派单人，派单人停用时通知同店管理员。提报检验通知指定检验人，退回通知维修工；人工催办通知当前处理人，同任务同收件人十分钟限一次。

通知与业务操作同事务入库。页面分别展示待发送、平台受理、发送成功、失败、结果未知。发送成功不表示员工接单。

- 明确的临时失败最多尝试五次，按退避间隔处理；明确失败可在详情里人工重试。
- 平台返回任务编号后查询发送结果，最多查询二十次。查询耗尽仍未知时保留任务编号和错误，人工核对钉钉记录。
- 发出请求前先持久化为结果未知。进程中断或发送超时且没有平台任务编号时，不盲目重发，避免重复通知。人工核对这类记录后再决定后续业务处理；页面不提供无依据重发按钮。
- 旧消息链接重新检查门店与当前完整员工名单，改派移除的成员无法再读取任务或维修附件。

## 接口和实现结构

共享契约在 `shared/types.ts`，前端业务集中于 `client/src/features/dispatch`。HTTP 路由、派工服务、领域规则、数据库仓储和钉钉集成分别独立。状态由领域规则计算，在同一事务中写入任务、原委托单/项目镜像、事件和通知。签字/润丰同步沿用既有流程，平台同步不会重置维修状态。

- `GET /api/dispatch/tasks`：筛选任务。参数为 `executionMode`（internal / field / outsourced）、`search`、`technicianId`、`stage`、`metric`、`urgent`、`overdue`、`from`、`to`；日期格式 `YYYY-MM-DD`，结束日包含整天。
- `GET /api/dispatch/technicians`：本店维修工汇总；`GET /api/dispatch/technicians/:id/tasks`：人员任务明细。
- `GET /api/dispatch/people`：可指派维修工和可选检验人；`GET /api/dispatch/tasks/:orderId`：详情、事件、通知、维修附件。
- `POST /api/dispatch/tasks/:orderId/actions`：接收共享的 `DispatchActionRequest`。每次操作必须携带 `expectedVersion` 和唯一 `requestId`；不确定是否提交成功时重用原请求编号及完整原请求。同编号不同内容返回 409。
- 姓名不是归属依据；全部使用内部员工 ID。旧状态接口不允许直接进入维修中/待结算；旧项目操作路径需要版本和请求编号，转入同一派工业务校验，禁止另行按项目分派。

## 本地验证

`npm run check` 执行单位测试、类型检查和生产构建。

数据库集成测试必须显式提供本机 PostgreSQL 管理连接，不读取业务 `.env`：

```sh
DISPATCH_TEST_ADMIN_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres node --test test/dispatch.integration.test.mjs
```

测试新建并自动删除 `codex_dispatch_test_*` 数据库，验证迁移、并发、幂等、返工、权限、附件、通知租约和平台同步兼容。不会操作现有业务库；跳过无关的集群级旧角色删除迁移。普通 `npm run check` 未配置此变量时跳过该独立测试。

额外设置 `DISPATCH_UI_TEST=true` 可运行桌面与 390px 手机浏览器闭环测试。需要可用的 Playwright 和 Chrome；可用 `DISPATCH_PLAYWRIGHT_MODULE` 指定模块路径、`DISPATCH_CHROME_PATH` 指定浏览器路径。先运行生产构建。截图输出至 `/tmp/repair-dispatch-qa`，所有消息均为模拟。

## 开单预选与签字后派工

服务顾问与管理员均可使用派工台及维修工详情。原派单员账号和钉钉映射迁移为服务顾问，员工 ID 与历史记录保留，不再提供独立派单员角色。

开单时可预选同店在职维修工，并填写预计完工时间、加急和备注；保存草稿时不生成维修任务或通知。客户签字时在同一事务中生成待接单任务、通知发件箱和润丰提交记录。未预选时可在签字提交润丰后点击“前往派工”，不依赖润丰回填完成。

预选人员在签字前停用、转店或角色变化时不阻止客户签字，开单详情提示重新指派。通知成功仍不等于接单。部署必须先应用 `202609110002_advisor_dispatch_plans.sql`，再启动新服务端和前端。

## 多人分工、外修与外包

部署前按顺序应用新增迁移 `202609140001_dispatch_execution_modes.sql`，再启动新版本；该迁移允许外包草稿没有维修员工，并为多人查询新增索引。已有单人任务与草稿兼容读取，不必重派。

- 维修员工为平级多选，不设主责、不按人分配项目。任一所选员工确认接单即代表整单接单，大家共同维护项目进度；并发操作沿用版本校验，事件记录实际操作人。无法接单仍暂停整单接单，等待服务顾问协调。
- 外修表示本店员工到其他单位维修车辆。服务单位、施工地址必填，可记录联系人、出发时间、预计返回及实际返回时间；多人外修均计入个人负荷。
- 外包分为承包方到店施工、车辆外送整包维修；承包方和施工方式必填，可记录施工地址、联系人、约定费用，车辆外送还可记录交车和收车时间。费用仅记录约定金额，不自动生成应付或变更结算。服务顾问和管理员代录接单、开工、项目完成和提报检验；维修员工不会获得外包任务访问权限。
- 三种执行方式均按现有整单/项目进度推进，全部项目检验通过后进入待结算。当前维修成员、曾录入开工或完成的人员不能自检，即便后续改派或返工也保留历史参与人限制。
- 变更员工、执行方式、承包方或外包施工方式走“改派”并填写交接说明；联系人、时间及约定费用在“调整派工信息”维护。完成后信息锁定。
- 开单预选支持相同信息。勾选“签字后自动派工”后填写，保存草稿不发送消息，客户签字时才激活任务与通知。

`technicianIds` 是完整平级员工名单；旧 `technicianId` 仅作为兼容字段保留，不代表主责。外包的名单为空；执行详情存于任务 JSON 和草稿 `execution_data`，API 路径保持不变。

## 派工台默认范围与状态筛选

派工台默认展示同店所有未完结工单，包含草稿、待客户签字、未派工、未接单、待开工、维修中、暂停、待检验及待结算。仅工单状态为“完成”的已完结工单默认隐藏；维修完成但尚未结算的工单保留，且不受完成日期限制。

顶部状态筛选支持以上各状态及显式查看已完结记录；切换状态会清除个人数量筛选，重置筛选恢复全部未完结工单。服务顾问和管理员可查看未签字工单详情，服务端禁止签字前执行派工操作。原始 API 阶段值保持兼容，新增 `stage=草稿/待客户签字/待结算/完成`；界面“未派工”“未接单”“正在维修”分别对应原有“待派工”“待接单”“维修中”。

## 实际工时与技师测试数据

实际工时按整张工单记录，单位为小时，允许两位小数，范围为大于 0 至 10000。服务顾问（包含原派单员）和管理员通过任务详情的“录入工时”填写；维修技师与检验员只能查看。维修中、暂停、待检验、维修完成但未最终完结的工单可填写；修改已有工时须写原因，记录前后数值、操作人和时间。已完结后锁定。

检验通过仍进入待结算；从待结算最终转为“完成”时，服务端在同一事务内校验工时已由调度人员录入。旧单尚未填写的也需要补录；不会根据开工/完工时间自动推算。该数据使用任务现有 JSON 字段，无新增数据库表或列。

本机运行 `npm run mock:technician` 创建 7 张分配给 `维修工（测试）` 的模拟工单，编号 `WT-MOCK-TECH-01` 至 `07`，覆盖待接单、待开工、维修中、外修暂停、待检验、返工、待录工时。只读取 `.env.local`，拒绝非本机或非开发环境；重复运行跳过已有单据，不覆盖测试进度，不发送通知、不产生润丰同步任务。
