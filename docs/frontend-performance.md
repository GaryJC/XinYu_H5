# 前端加载与构建体积

运行 `npm run check` 后执行 `npm run analyze:bundle`，可查看各入口的 JS/CSS 依赖总量、gzip 估算值和静态资源总量。报告会递归计算静态依赖并去重；工作台统计包含应用外壳和工作台页面，不能只用入口 JS 的大小代表首屏。

## 2026-11-03 优化

在同一工作区、相同依赖和构建环境下对比（十进制 MB/KB）：

| 指标 | 优化前 | 优化后 | 减少 |
| --- | ---: | ---: | ---: |
| 全部静态资源 | 18.47 MB | 10.34 MB | 44.0% |
| 工作台首屏 JS/CSS | 2.17 MB | 1.62 MB | 25.3% |
| 工作台首屏 JS/CSS gzip 估算 | 760 KB | 517 KB | 31.9% |

首屏统计不包括 API 数据、业务照片、后续交互和字体下载；gzip 是逐文件压缩的估算，不是线上网络实测。新增 manifest 不计入静态资源总量。

- 打印预览、模板和字体样式在生成预览时加载，PDF 引擎仍在生成 PDF 时加载。字体不再以内联 base64 混入 JS。
- 保留 Noto Serif SC 的两个字重和全部 Unicode 字形分片，仅输出 WOFF2，移除重复的 WOFF。目标仍是 Chrome 80 / Safari 13，旧 WebView 的 CSS 兼容配置保持不变。
- 工作台、客户签字和供应商入口分别加载，外部客户入口不再拉取整个工作台。
- 修改联系及车辆信息时才加载新增车型/单位组件及拼音字典。
- 派工负荷图表展开时才加载 ECharts 和请求负荷数据；文字标签与图表实现分离，避免列表间接导入图表库。

图表和 PDF 分块仍约 600 KB（未压缩），属于交互时加载的资源，不计入首屏。不通过关闭构建告警掩盖这些体积。

构建配置使用 Vite 的[按需分块和静态资源处理](https://vite.dev/guide/assets)及[构建 manifest](https://vite.dev/config/build-options.html)。分析脚本会检查三个入口是否意外静态依赖打印、图表或拼音模块，以及是否重新输出重复 WOFF。

## 部署缓存

Nginx 直接提供前端时，采用 [部署指南](./deploy-ecs.md) 中 `/assets/` 的一年 immutable 缓存配置，并保持 HTML 和版本接口 `no-store`。仅带内容哈希的构建资源适用长期缓存，缺失资源返回 404。修改文档不会自动更新现有服务器的 Nginx 配置。

## 2026-11-09 稳定性优化的构建门禁

`npm run check` 已包含包体分析。工作台口径包含应用外壳、工作台及默认显示的移动归档列表，不能只计算懒加载前的外壳。桌面表格单独加载，打开详情、打印、签字和修改资料时才加载对应模块；供应商页不再间接加载内部采购管理详情。

本轮修改前基线：工作台 520,762 字节、客户签字 218,711 字节、供应商 380,080 字节（逐文件 gzip 估算）。构建上限分别为 450,000 / 225,273 / 391,483 字节；后两项是本轮基线的 103%。构建失败必须修正依赖或说明预算调整，不能通过删掉默认展示的归档依赖来缩小统计口径。

离线查询对比入口：`RELEASE_TEST_ADMIN_URL=<专用本地测试库> node --expose-gc scripts/benchmark-dispatch.mjs`。脚本在事务内创建临时表，生成 1 千、1 万、5 万单，对照未下推候选条件的领域实现；比较有序结果与所有标签计数，交替采样避免先后次序偏差，结束回滚。输出 P50/P95、实际读取候选行数、领域结果字节和测试进程 RSS。它不是线上 HTTP 延迟，也不代表生产进程内存。

最终本机 gzip 估算：工作台 412337、签字 222367、供应商 282020 字节。5 万单筛选查询 P95 968→426 ms，无筛选 964→966 ms。13 个角色/查询对照在三个规模均一致。监测 P50 基本持平，但 P95 采样波动，监测总开销不超过 3% 的目标仍待持续实测；不得将它标记为已通过。完整数值及限制见 HANDOFF.MD。

### 本地监测复验（2026-11-09）

旧监测实验仅 12 个有效样本，其 P95 实际取最大值，并在每个请求前强制 GC。新的 `--observability` 模式采用 10 对预热、120 对交替采样、自然 GC，并单独测量业务计算之外的计时/日志包装耗时；普通候选集对比模式不变。

本次无筛选 P95 为 144.84→143.86 ms，个人筛选 36.47→37.15 ms（+1.85%），前台本地样本满足 3% 目标。包装自身 P95 分别 0.198/0.067 ms。它解释了为何不能把旧单个极值归因于计时代码，但不证明所有设备和负载下都低于预算。

`node scripts/benchmark-queue-metrics.mjs` 从实际 worker 捕获查询，在事务临时表中测量四个队列各 5 万条全部 pending 的保守夹具；20 次采样一轮 P95 为 49.38 ms，占 60 秒周期约 0.082% 的墙钟时间。此比例不是数据库 CPU 或对前台响应的影响，不与前台百分比相加。线上总监测开销仍需实际负载验证。机器可读结果保存在 `output/optimization-local-acceptance.json`。
