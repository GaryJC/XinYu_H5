批量发送、批量确认，逐人保留结果

2026年11月11日 · 基于当前仓库的实施建议。尚未修改业务代码或部署。

员工收到的通知保持一致

保留通知内容、链接、接收资格、提醒频率和业务提交时的实时权限校验。优化发生在后台：同一次业务事件中，符合条件的相同消息共享一次发送任务。

例如同一条待检验通知发给3名合格检验员：原来3次发送＋3次查询；改后1次发送＋1次查询。三人仍各收到同一条通知。正常一次确认时，该组由6次降到2次；这是单组示例，不是整月降幅预测。

具体改动顺序

  1. 先核算可合并比例。从现有数据库通知记录按业务来源、事件、内容统计单人和多人组，单列重试及查询次数。核算不调用钉钉，不输出通知正文、凭据或完整人员资料。历史记录缺少事件标识时采用保守估计，不按相似文字猜测。
  2. 先接入派工通知链路。保留原逐人记录和业务校验，新增持久化发送批次、成员关联、实际发送的钉钉账号快照、平台任务编号及批次租约。新增数据库迁移，保留现有接口和状态展示。
  3. 校验后再合并。逐人生成最终消息，仅同应用、同业务来源与门店、同事件及轮次、相同类型、完整正文和链接完全相同的待发送记录合并。配件通知会按人重新计算内容，必须在计算之后分组；不能只比较工单号或原始摘要。首版限制小批次，核对官方发送与结果查询限制后确定上限。没有可靠事件标识的旧记录继续单发。只合并已经就绪的通知，不额外等人凑批。
  4. 按批次查询，按人员归档。同一平台任务每轮只查询一次，再分别更新成功、失败、待确认人员。已确认成功者不随他人失败而重发；结果未就绪时沿用退避，不为查询已读状态持续轮询。
  5. 通过验收后复用于其他通知。依次接入出车、竞价、行驶证和保险通知，保留各自的业务权限和模板。签字重签、补签等没有普通派工事件编号的链路，先明确独立事件标识再接入；纸质委托的特殊分发规则单独核对。不同业务、不同轮次、不同项目的真实提醒不混成一条。

必须保留的可靠性边界

  • 发送前仍检查员工启用状态、门店和岗位、当前项目归属、工单状态及原业务规则。多人维修、返工、回审、改派不能因为合并而共享错误权限或项目内容。
  • 批次和成员关联原子写入；多个后台进程只能领取同一批次一次。数据库事务结束后再调用钉钉，不持有数据库行锁等待远程发送。小批次和明确的租约时限必须覆盖校验与发送用时，旧租约不得覆盖新结果。
  • 有平台任务编号时，重启后继续查询；发送超时且没有任务编号时保留“结果待确认”，不自动重发。批量发送不能消除平台已接受但响应丢失的不可判定窗口。
  • 查询按实际发送的钉钉账号快照归属，避免员工后来解绑或换绑导致结果对应错人。部分失败只影响对应人员；人工重试明确失败者时新建批次，不重发已成功成员。
  • 已受理或结果未知的旧任务沿用旧恢复流程，不重新打包发送。缺失、未知或相互矛盾的结果不标记成功。

测试与验收

检查通过标准
调用次数三人同消息夹具：3发＋3查变成1发＋1查；单人仍为1发＋1查；同一任务的并发查询只产生一次远程请求。
内容与权限逐人核对前后消息及链接一致；撤权、停用、改派、返工、跨轮次、部分备料及禁止自检规则有效。
失败与恢复部分成功、明确失败、未知结果、网络中断、保存任务编号失败、多进程抢占、旧租约回写、重启恢复和人工重试均有回归。
本地检查运行专项通知测试、npm run check 和隔离 PostgreSQL 发布检查；关键数据库套件零跳过，不发送真实测试通知。
性能与开销不增加定时扫描频率；新增领取查询有对应索引。对比同数据的队列 SQL 次数、P50/P95、锁等待与 RSS，并记录实际 OpenAPI 请求减少量；不以增加权限结果缓存换额度。

节省多少，取决于多人组占比

如果510条逐人通知最终能归为300个发送批次，且每批正常查询一次，相关调用就会从1020次降到600次，减少约41%。如果大多只有一个接收人，收益会明显更小。必须先统计，不能预先承诺减半或保证本月额度够用。

免登、角色列表、角色成员、用户详情属于官方免计量清单，本轮省月额度以工作通知为重点。组织其他应用的消耗需要另行核对。
