可行。建议保留现有 React 页面、Node 服务和数据库，先让身份与权限脱离钉钉，再做可安装的客户端。

按当前代码评估，2026 年 11 月 11 日。本文是方案，不是已实施的迁移；尚未统计员工手机型号、系统版本或实际后台推送到达率。

现有系统怎么处理

模块建议需要补齐
工单、派工、检验、采购、用车复用现有业务接口、数据库和大部分页面验证普通浏览器与独立客户端的拍照、上传、下载、返回导航和通知跳转；不是直接打包即可交付。
登录新增正式独立登录，复用现有会话和权限骨架可采用管理员开户＋账号密码；若使用短信则另计成本。需有重置、限速、设备会话与离职停用。现有测试身份入口不能作为正式登录。
员工、门店、岗位由系统自己管理建立独立员工 ID，将钉钉账号变成可选绑定；沿用原业务用户 ID或明确映射，避免历史负责人、附件权限和润丰绑定断链。经办归属逐步从姓名迁至 ID，不凭重名自动合并。
人员名单替换各业务中的钉钉角色名单同步登录独立还不够，派工、检验和通知读取岗位也须使用自管员工数据；否则依然依赖钉钉。
通知应用内待办／消息中心为记录，手机推送为提醒渠道复用业务事件、去重及投递记录思路；新增设备注册、失效令牌清理和通知链接。先保存待办，再异步推送；推送失败不丢待办。
照片、签字、文件保留现有存储和网页签字替换钉盘保存／预览为系统分享或下载；客户和供应商继续用网页链接，通常不必安装员工 App。
润丰、数据库、云存储／识别继续保留检查员工映射和认证边界；脱离钉钉不等于脱离这些后端服务，其运行成本仍存在。

选择哪种客户端

路线适合情况取舍
独立网站先去除钉钉登录限制，电脑和手机直接访问改动相对少；普通网页关闭后的通知不能靠前台长连接保证。
PWA（安装到桌面的网页）低成本试用、网页体验基本够用iOS/iPadOS 16.4 起，添加到主屏幕的 Web App 支持 Web Push，需用户授权；必须在员工实际设备和网络验证。WebKit 官方说明
现有网页＋原生容器希望保留现有页面，又需要独立安装与设备功能建议优先评估 Capacitor，可接入现有 JavaScript 项目并构建 iOS/Android 应用。仍需适配相机、存储、推送、深链接和发布。官方文档
重写移动客户端有明确的重度原生交互需求投入更大。当前以表单、列表、照片和审批为主，暂未看到必须整体重写的理由；这是基于现有项目的判断。

推送是主要验收难点

Capacitor 官方 Android 推送插件使用 FCM，不能仅装插件就认定覆盖员工所有手机。若以国内手机为主，应按设备清单评估厂商通道或聚合推送服务，并进行锁屏、后台、重启、通知权限关闭后的测试。原生鸿蒙须单独评估客户端适配，不能把 Android 包兼容性当作前提。

阿里云文档列有华为、小米、荣耀、OPPO、vivo 等厂商通道；具体选择须看实际机型、网络、服务条款及费用。本方案不承诺推送永久免费或必达。Capacitor 推送文档 · 阿里云厂商通道说明

建议迁移顺序

  1. 确认员工设备、安装分发方式和关键通知要求，确定首批平台。
  2. 增加独立登录与员工岗位管理，迁移身份映射；与钉钉入口暂时共用同一套业务数据。
  3. 建立应用内消息中心，把“谁需要处理”与“通过哪个渠道提醒”分开，避免两端重复通知。
  4. 选一店验证独立客户端：开单、派工、接单、检验、签字、用车和后台推送。
  5. 验证权限、身份停用、历史归属、通知去重及更新流程后，再停钉钉同步和发送。

成本与性能

钉钉通知额度限制可以移除，但会增加独立认证、设备推送、安装分发、升级和运维的成本。短信或第三方推送如采用则单独核算。没有设备清单和发布目标前，不给固定工期或费用承诺。

首版不默认支持离线提交。复用现有分页和图片压缩，不通过频繁后台轮询模拟推送；服务端采用有界队列和设备去重。试点比较首屏、照片上传、API P95、推送延迟、漏重通知、耗电和流量，与当前版本基线一起验收。

判断：如果只是为少花通知调用费，先优化现有系统更合适；如果希望长期拥有自己的员工系统、统一管理权限并持续扩展，独立 App 值得推进。
